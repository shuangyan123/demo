# 数据可靠性边界与演进计划

本文记录 0.3 阶段的数据事实、已有保护和后续演进顺序。它不是云同步方案，也不授权修改 `review_workspace` v16。

## 数据分类

| 分类 | 当前载体 | 典型数据 | 恢复原则 |
| --- | --- | --- | --- |
| 核心业务数据 | IndexedDB `review_workspace` v16 | 错题、复盘、知识、面试、辅导、对话、导入草稿、自动化定义与运行 | 用户不可无感丢失；迁移前必须可校验、可回滚 |
| 可重建数据 | 业务表中的派生结果或运行时重新计算 | 统计汇总、筛选结果、学习状态快照、搜索结果 | 优先从核心业务数据重建，不作为独立真相源 |
| 缓存与小型配置 | IndexedDB、版本化 `localStorage`、进程内缓存 | 模型目录缓存、UI 偏好、运行时快照 | 允许失效后重建；版本边界必须显式 |
| 凭据 | 密文记录与 `review_workspace_secure_keys` v1 | AI、额度、MCP、粉笔等凭据及不可导出 AES-GCM 主密钥 | 默认不导出；恢复后要求重新配置；不得降级为明文 |
| 外部 Vault 数据 | 用户选择的 Obsidian Vault 与本地 mapping/三方哈希 | 托管 Markdown、Wikilink、同步基线、冲突状态 | Vault 文件是外部真相源；应用不得静默覆盖冲突 |
| 临时数据 | 内存、对象 URL、`review_workspace_transfer` v1 | 原始媒体、厂商/MCP 原始响应、恢复暂存包与旧快照 | 用完即弃；崩溃恢复只保留完成回滚所需的最小信息 |

`review_extensions` v1 与核心数据库隔离，但其已安装声明记录属于本地业务配置，当前已进入完整导出与重置范围。

## 已有能力

### Backup / Export

- `LocalDataExportV2` 是当前唯一受支持的完整业务备份格式。
- 采用显式表白名单；新增表默认不会被静默导出。
- 导出递归移除密文、IV、Key、Token、Cookie、目录句柄和厂商原始响应。
- AI 连接只保留非敏感元数据，并标记为需要重新配置凭据。
- Obsidian Vault 正文与目录句柄不进入备份。

### Restore

- 导入包限制为 100MB，并校验 schema 版本、表白名单、记录结构、重复主键和关键悬空关联。
- 恢复前显示替换数量和凭据/Vault 重新配置提醒。
- `review_workspace_transfer` v1 暂存待提交包和旧快照；恢复失败时回滚，完成后清理。
- 恢复不改变核心 Dexie v16，也不恢复加密主密钥。

### Health Check

- 配置健康与本地诊断已经覆盖浏览器安全上下文、关键默认连接和 Obsidian 连接状态。
- 数据管理面板提供各业务域的真实记录数量，危险操作前不使用估算值。
- Vault 同步继续使用目录预检、稳定 `review-id`、三方哈希与冲突状态。

### Repair

- 当前可靠修复路径是“恢复已验证备份”“重新选择 Vault”“重新输入凭据”或按业务域清理。
- 完整重置会删除核心库、扩展库和安全密钥库，并清理本应用命名空间内的配置。
- 当前没有自动改写业务记录的通用 Repair；这是刻意限制，避免诊断逻辑成为新的破坏入口。

## 缺口与后续顺序

1. **只读完整性报告**：复用恢复校验规则检查当前库的关键引用、表计数和数据库可打开性；只报告，不自动修复。
2. **备份清单**：为导出增加可读的表计数与格式版本摘要；是否加入文件级校验和需先评估浏览器大文件成本。
3. **恢复演练**：在隔离的临时库中验证包可应用，再进入现有替换事务；不得绕过 `LocalDataExportV2`。
4. **定向修复**：只为有明确、可复现损坏模式的记录提供修复，并要求预览、备份和结果复核。
5. **Vault 健康报告**：汇总重复 `review-id`、断开 mapping、过期哈希和冲突，不把“修复”解释为覆盖用户文件。

## 验收与回滚边界

- 任何数据可靠性改动都必须证明旧 v16 数据可直接打开，导出后不含凭据/Vault 正文，恢复失败可回到原快照。
- 不因报表、缓存或前端分页新增 Dexie 索引；只有真实慢查询证据和独立迁移方案才能讨论版本升级。
- Repair 必须可在执行前取消，并可通过刚生成的备份回滚；无法完整回滚的 Vault 写入必须逐项报告。
- 不引入账号、云数据库、强制同步或多租户模型。
